# 54. Verify update safety through the installed console, and bind it to the release candidate

## Status

Accepted

## Context

[Issue #195 / CF-22.03](https://github.com/Sandsy09/create-forge/issues/195) is
the third and last child of
[CF-EPIC-22](https://github.com/Sandsy09/create-forge/issues/188). Its
predecessors are merged: CF-22.01
([ADR 0052](0052-contain-every-client-filesystem-target.md), #207) contains
every engine-update filesystem target, and CF-22.02
([ADR 0053](0053-recover-updates-from-the-actual-git-state.md), #208) prints
recovery guidance read from the repository's real Git state. Both are proven
against `create_forge.update`'s own functions, with real Git and real files.
Neither is proven through what a user runs: the wheel's console script, the
engine PyPI serves, the process boundary between them.

The issue also blocks
[CF-21.03 (#167)](https://github.com/Sandsy09/create-forge/issues/167), whose
criteria require that the final candidate carry both fixes, that the exact
candidate hashes be recorded for the safety and the Streamlit validation, and
that affected evidence be refreshed if the candidate changes. Four facts shape
how that is delivered:

- **`release.yml` runs no tests.** It checks the wheel, the changelog, the tag
  and the notes, and relies on `main` being green.
- **The Windows e2e job runs a hand-picked list of tests**, so a new installed
  module is silently absent from Windows unless it is named there.
- **The installed console cannot, by itself, produce what needs proving.** With
  the recorded provider equal to the installed one every target classifies
  `unchanged`, and a subprocess offers no failure injection. The one existing
  installed update test shows only that a conflict is left untouched.
- **The release wheel will not have this candidate's hash.** CF-21.03 bumps the
  version, so the artefact it publishes differs from the one validated now.
  What can be bound today is the source that behaviour comes from, the provider
  artefacts, and this commit's artefacts; what CF-21.03 needs is a way to
  refresh the same binding on its own commit.

## Decision

1. **Add one self-contained installed suite,**
   `tests/test_e2e_installed_update_safety.py`, reusing the shared harness and
   the session `installed_client` fixture (candidate wheel plus exactly
   `forge-template 0.6.0`). One project is generated by the installed console
   and copied per scenario, beside an outside directory holding a sentinel file
   no update may touch. It covers the normal route (a no-op update, a committed
   local edit preserved, `--dry-run`); the degraded route with a real changed,
   removed and added target staged by the real `git add -A`; `--dry-run` on both
   routes leaving the tree, index and status byte-identical; containment
   refusals, real and dry-run, degraded and normal, including a recorded Git-hook
   target, an invalid late target beside a valid changed one, and a symlinked
   parent; and both Git recovery states plus the dirty-tree case.

2. **Produce a real change by editing the recorded digests, and a real
   interruption with a pre-existing `.git/index.lock`.** `update --degraded`
   decides "pristine" from the recorded per-target digest in the committed
   `.forge/generation.json`; editing that file gives the installed console a
   genuinely changed, removed and added target without a second provider
   release. A lock makes the real `git add -A` fail after every file was
   written, which is exactly the unstaged, half-finished state an interruption
   leaves; it is removed before the printed recovery runs, as an interruption
   would have released it. The suite depends only on the `output[].target` and
   `digest` shape `update.read_recorded` already parses, so a provider change to
   it fails these tests loudly. The recovery test pastes the guidance the
   console *printed*, through a shell, from outside the repository.

3. **State what is not covered installed.** The normal route's real three-way
   *merge* needs an older provider render that differs from the installed one;
   `tests/test_update_engine.py` proves it. Renames are unreachable through any
   shipped template; the dry-run rename defect is
   [#209](https://github.com/Sandsy09/create-forge/issues/209). That an outside
   file is *not read* during `--dry-run` is proven at unit level, where reads can
   be observed; the installed suite proves it was neither changed nor removed.
   The symlinked-parent case is POSIX-only; its Windows counterpart, a junction,
   is proven at unit level.

4. **Bind the evidence with one reproducible tool, to a content digest rather
   than an archive hash.** `scripts/candidate_evidence.py`
   (`uv run poe evidence:candidate`) prints one table: the commit and whether the
   tree is clean, for the wheel and the sdist both the archive sha256 and a
   *content digest* (a sha256 over each member's name and bytes), the
   `forge-template` version with its sdist and wheel sha256 read from `uv.lock`,
   the uv, git and Python versions, and the safety-relevant source digest.
   **An archive sha256 is not a stable identity.** Building the same source in two
   build environments gave wheels with byte-identical members, in the same order,
   with the same timestamps and attributes, and different archive sha256, because
   the compressed streams differ; repeated builds in *one* environment are
   identical, which is easy to mistake for reproducibility. The content digest is
   independent of compression and is what two builds of the same candidate share,
   so it is the binding the record relies on; the archive sha256 is recorded as
   informational and for comparison with what PyPI serves. Measured: the wheel
   built from this change and the wheel built from the base commit `7c80208` have
   different archive hashes and the **same** content digest, which shows this
   change ships exactly what `main` already did. CF-21.03 re-runs the tool on the
   release commit to refresh the binding rather than write it again by hand.

5. **Fail `main` when the evidence goes stale.** `safety_digest` is a sha256
   over `paths.py`, `update.py` and `staging.py`, plus only the update functions
   of `cli.py` (`update_project`, `_run_engine_update`, `_print_recovery`,
   `_confirm_degraded`, extracted with `ast`), with line endings normalised so
   a Windows checkout and a Linux one agree. The record stores it, and
   `tests/test_update_safety_evidence.py` recomputes it and fails with an
   instruction to re-run the installed suite and refresh the record. Hashing
   functions rather than all of `cli.py` means an unrelated edit does not force a
   refresh, which would otherwise teach people to refresh without re-running
   anything. This is a nudge with teeth, not a proof: updating the digest without
   re-running the suite satisfies it, and the record and this decision say so.

6. **Run the suite on Windows.** The `e2e-windows` job gains a step for the new
   module, and the guard test asserts it stays named there. The Linux `e2e` job
   already runs every `e2e`-marked test.

7. **Make the prerequisite explicit without touching `release.yml`.** It lives in
   the record's release-prerequisite checklist, in CONTRIBUTING's Releasing
   steps, and here. Because `main` cannot stay green with stale evidence, cutting
   a release from a green `main` (CONTRIBUTING step 2) is implicitly gated. A hard
   step in the release workflow was considered and rejected: it would give the
   most sensitive workflow in the repository e2e runtime and network dependence,
   let a flaky run block a release, and change a workflow that ADR 0037 pins and
   that this issue's exclusions leave alone.

8. **Tie the suite to the versions it validates.** The suite asserts the console
   under test reports the client version this repository declares
   (`tests/installed_client.py`'s `CLIENT_VERSION`) and exactly the pinned
   provider. A release that bumps one without the other fails there instead of
   being validated as something it is not.

9. **Change nothing under `src/`.** This is evidence, tooling, documentation and
   one CI step. ADRs 0001-0053 are untouched.

## Consequences

- **An edit to a hashed file forces a refresh.** That is the intent. CF-25 (the
  CLI decomposition epic) will move the `cli.py` functions the digest extracts;
  `safety_digest` raises a clear error naming what to re-point rather than
  silently ceasing to cover them, and CF-25 must re-run the installed suite.
- **CF-21.03 inherits a checklist,** recorded in
  [update-safety-validation.md](../update-safety-validation.md): re-run
  `uv run poe evidence:candidate` on the release commit, confirm the guard is
  green (or refresh the installed evidence first), record the artefact hashes for
  both this suite and the Streamlit suite, and re-verify the published artefacts.
  The one CI run of a candidate covers both installed suites.
- **CI run ids live on the issue, not in the living record,** so no docs-only
  commit is needed to paste one. The record holds what is stable: the map from
  criteria to tests, the procedure, the digest, the provider artefacts and the
  local outcomes.
- **The e2e tier gains a seventh module.** Its measured runtime is recorded in
  the record against the Linux 60-minute and Windows 45-minute job limits rather
  than assumed.
- **The canonical documents move with it:**
  [end-to-end-tests.md](../end-to-end-tests.md),
  [installed-streamlit-validation.md](../installed-streamlit-validation.md), the
  [docs index](../README.md) and CONTRIBUTING.
- **Out of scope:** any release, version bump or publication; non-UTF-8 Windows
  settings ([CF-23.02, #197](https://github.com/Sandsy09/create-forge/issues/197));
  the local `cp1252` harness decoding defect
  ([CF-23.01, #196](https://github.com/Sandsy09/create-forge/issues/196)).
