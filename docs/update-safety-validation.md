# Installed update-safety validation

This is the living evidence record for
[CF-22.03 / #195](https://github.com/Sandsy09/create-forge/issues/195), the third
and last child of
[CF-EPIC-22](https://github.com/Sandsy09/create-forge/issues/188). It proves
CF-22.01's containment
([ADR 0052](adr/0052-contain-every-client-filesystem-target.md)) and CF-22.02's
recovery ([ADR 0053](adr/0053-recover-updates-from-the-actual-git-state.md))
through the **installed console** — the built wheel, paired with the published
`forge-template 0.6.0` — rather than through `create_forge.update`'s own
functions, and binds that evidence to the release candidate. The decision is
accepted under
[ADR 0054](adr/0054-verify-installed-update-safety-on-the-release-candidate.md).

It blocks [CF-21.03 (#167)](https://github.com/Sandsy09/create-forge/issues/167):
the [release prerequisite](#release-prerequisite) below is what that issue
completes before publishing.

## What this proves, and what it does not

**Proves**, against a real generated project, a real Git repository, and an
outside sentinel file no update may touch:

- containment and recovery hold through the shipped console, on Linux and
  Windows CI;
- the suite **fails on a candidate that lacks the fixes**: run against the commit
  before CF-22.01 and CF-22.02, whose update path is byte-identical to published
  `0.4.0`'s, seven of its tests fail (see [Pre-fix result](#pre-fix-result));
- the evidence is tied to the versions it validates and cannot silently go stale.

**Does not prove**, and says so:

- the normal route's real three-way **merge**. With the recorded provider equal
  to the installed one every target classifies `unchanged`, and a merge needs an
  older provider render that differs. `tests/test_update_engine.py` proves it.
- **renames.** No shipped template declares one, and `--dry-run` with a rename
  is an open defect, [#209](https://github.com/Sandsy09/create-forge/issues/209).
- that an outside file is **not read** during `--dry-run`. Reads cannot be
  observed through a subprocess; `test_dry_run_reads_nothing_outside_the_project`
  and `test_a_tampered_recorded_target_is_not_read_in_a_dry_run` prove it at unit
  level, and the installed suite proves the file is unchanged and the update is
  refused before anything else changes.
- a symlinked parent on Windows. The installed case is POSIX-only; a Windows
  junction and a symlink are proven at unit level by
  `test_a_windows_junction_that_escapes_is_refused` and
  `test_a_new_file_under_an_escaping_linked_parent_writes_nothing_outside`.

## The installed suite

`tests/test_e2e_installed_update_safety.py` reuses the shared harness and the
session `installed_client` fixture. One project is generated by the installed
console and copied per scenario, beside an outside directory holding a sentinel
file.

| Group | Test | Proves |
| --- | --- | --- |
| Normal route | `test_normal_route_no_op_update_changes_nothing` | exit 0, "Nothing changed", HEAD, index and status untouched |
| | `test_normal_route_update_preserves_a_committed_local_edit` | a committed local edit survives an update |
| | `test_normal_route_dry_run_writes_nothing` | dry-run leaves the tree, index and status byte-identical |
| Degraded route | `test_degraded_update_applies_a_real_changed_removed_and_added_target` | a real changed, removed and added target, all staged by the real `git add -A`, metadata refreshed with a degraded reason |
| Dry-run | `test_degraded_dry_run_lists_every_target_and_writes_nothing` | the classification list for all three, nothing written, sentinel untouched |
| Containment | `test_degraded_update_refuses_a_recorded_target_outside_the_project` | real and dry-run: exit 1, "unsafe update target", "nothing to recover", no restore command, sentinel and project unchanged |
| | `test_normal_route_refuses_a_tampered_recorded_document` | refused on the engine-native route too |
| | `test_a_recorded_git_hook_target_is_refused_and_left_alone` | a recorded `.git/hooks/pre-commit` is refused and the hook untouched |
| | `test_an_invalid_late_target_leaves_a_valid_changed_target_unwritten` | whole-update preflight: a valid changed target is not written when a later one is bad |
| | `test_a_symlinked_parent_that_escapes_is_refused` | POSIX only |
| Recovery | `test_the_documented_recovery_restores_a_completed_staged_update` | the documented commands restore the committed baseline and leave an ignored user file alone |
| | `test_an_interrupted_update_prints_guidance_that_recovers_it` | a real interruption; the *printed* commands, pasted through a shell from outside the repo, restore the baseline |
| | `test_a_dirty_tree_is_refused_without_offering_to_discard_it` | no recovery command is offered; the user's edits are intact |

### How the installed console is made to produce real changes

The console cannot, on its own, produce a changed update offline, and a
subprocess offers no failure injection, so the suite uses two techniques:

- **A genuinely changed update.** `update --degraded` decides "pristine" from the
  recorded per-target digest in the committed `.forge/generation.json`. Setting a
  locally edited README's recorded digest to match it, adding a recorded entry
  (with a matching file) for a target the template no longer renders, and
  deleting a generated file yields a real changed, removed and added target. The
  suite depends only on the `output[].target`/`digest` shape
  `update.read_recorded` already parses.
- **A real interruption.** A pre-existing `.git/index.lock` makes the real
  `git add -A` fail after every file has been written: the unstaged,
  half-finished state an interrupted update leaves. `git status` succeeds with the
  lock present, so the clean-tree precondition passes and the update begins. The
  lock is removed before the printed recovery runs, as an interruption would have
  released it.

## Pre-fix result

To show the suite has teeth on the installed candidate, it was run unchanged
against a scratch worktree at `11c42f7` — the last commit before CF-22.01 and
CF-22.02. `git diff v0.4.0 11c42f7` is empty for `update.py`, `staging.py`,
`lifecycle.py` and `cli.py`, so the update path there is that of published
`0.4.0`. **Seven tests failed, seven passed, one skipped**, and the failures are
exactly the ones about the fixes:

| Test | What the pre-fix console did |
| --- | --- |
| `test_degraded_update_refuses_a_recorded_target_outside_the_project[real]` | exit **0**, "1 clean": the recorded target outside the project was processed |
| `test_degraded_update_refuses_a_recorded_target_outside_the_project[dry-run]` | exit **0**, listed `removed clean ../outside/sentinel.txt`: the outside file was read and classified in a dry run |
| `test_normal_route_refuses_a_tampered_recorded_document` | refused by the provider, but printed `Recover with: git restore . && git clean -fd` where nothing had changed |
| `test_a_recorded_git_hook_target_is_refused_and_left_alone` | exit **0**, "1 clean": a recorded Git-hook target was processed |
| `test_an_invalid_late_target_leaves_a_valid_changed_target_unwritten` | exit **0**, "2 clean": the valid target was written *and* the bad one processed |
| `test_an_interrupted_update_prints_guidance_that_recovers_it` | printed only the retired `git restore . && git clean -fd`; no restoring command |
| `test_a_dirty_tree_is_refused_without_offering_to_discard_it` | printed `Recover with: git restore . && git clean -fd` on a refusal to start, offering to discard the user's own work |

The seven passing tests are the ones that do not depend on the fixes (the version
binding, the no-op and dry-run routes, the degraded change, the documented
recovery, which uses the corrected commands directly). The worktree was removed
afterwards.

## Findings

1. **A no-op `update` rewrites the metadata file's line endings on Windows.**
   [engine-project-lifecycle.md](engine-project-lifecycle.md) rule 15 says a
   repeated no-op update rewrites `.forge/generation.json` "to byte-identical
   content". `update.write_recorded` (and the `cli.py` code it replaced) writes
   with `Path.write_text`, which translates `\n` to `\r\n` on Windows, so the
   bytes change. Generated projects hide it because they ship `.gitattributes`
   with `* text=auto eol=lf`; a project without that file would show a spurious
   diff on every no-op update. Pre-existing, not introduced by CF-22.01 or
   CF-22.02, and not fixed here: this issue changes nothing under `src/`. The
   installed suite compares that one file modulo line endings and everything else
   exactly, and HEAD, the index and the status exactly. A separate issue is
   proposed.
2. **On the engine-native route the provider refuses a tampered recorded
   document first.** A schema-valid recorded entry whose target escapes the
   project is refused by `forge-template` (`invalid-generation-metadata`: "the
   supplied old render does not match the recorded output target set") before the
   client's boundary is reached, and the client reports "nothing to recover". The
   client's boundary is therefore defence in depth on that route, and is exercised
   installed by the degraded route.
3. **An archive hash is not a stable identity** — see [Candidate
   binding](#candidate-binding).
4. **Fixed:** `--dry-run` no longer runs `git mv` when the plan has a rename
   ([#209](https://github.com/Sandsy09/create-forge/issues/209)).
   `apply_renames` now takes a required `dry_run` keyword and returns after
   validating both endpoints, before moving anything; `apply_plan` reads a
   renamed target's working bytes from its still-in-place old path so the
   preview classifies exactly as a real run would. There is still no
   *installed* rename case: the rename plan comes from the provider, no
   shipped component declares one (rule 11: "the catalogue declares none
   today"), and the installed console cannot be made to emit one without a
   fixture provider. The evidence is the fast suite instead, which runs on
   both Linux and Windows: `tests/test_update_engine.py`'s
   `test_a_dry_run_and_a_real_run_classify_a_rename_identically` (pristine and
   locally-edited variants) and `tests/test_cli.py`'s
   `test_engine_update_dry_run_with_a_rename_leaves_the_tree_and_index_untouched`,
   the issue's own reproduction reduced to a test, confirmed to fail against
   the pre-fix code.

## Release prerequisite

CF-21.03 ([#167](https://github.com/Sandsy09/create-forge/issues/167)) must not
publish until every item is done **on the release commit**:

- [ ] `uv run pytest tests/test_update_safety_evidence.py` is green, which means
  the safety-relevant source is what the recorded digest describes. If it is red,
  re-run `uv run pytest tests/test_e2e_installed_update_safety.py`, then refresh
  the [Candidate binding](#candidate-binding) table and the digest in this record
  first.
- [ ] `uv run poe evidence:candidate` is run on the release commit, with a clean
  tree, and its table recorded in the release validation record. Compare the
  **wheel content digest** with the row above: a match shows the release ships
  the same code that was validated; a mismatch means something that ships
  changed, and the affected evidence is refreshed before publication.
- [ ] Both installed suites — this one and the Streamlit suite
  ([installed-streamlit-validation.md](installed-streamlit-validation.md)) — pass
  in the protected CI run of that commit, and both candidate hashes are recorded.
- [ ] `CLIENT_VERSION` in `tests/installed_client.py` matches the released version
  (`test_the_suite_runs_against_the_candidate_and_the_pinned_provider` fails
  otherwise).
- [ ] After publication, the published artefact is verified: install it and run
  `test_the_suite_runs_against_the_candidate_and_the_pinned_provider`'s checks
  (`--version`, `doctor --json`), and compare the PyPI file's sha256 with the one
  the release job built.
- [ ] The corrected `0.4.0` guidance is live and the `v0.4.0` release notes point
  at it (done for CF-22.02; confirm at release).

## Boundaries retained

This is evidence, tooling, documentation and one CI step. It changes nothing under
`src/`, no CLI surface, dependency, protocol, lock or generated byte, and it does
not touch `release.yml`.

When this evidence changes, update this record, the
[end-to-end tests contract](end-to-end-tests.md) and the executable suite in the
same pull request.
