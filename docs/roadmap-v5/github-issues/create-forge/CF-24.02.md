# CF-24.02 — Add actionable dependency-vulnerability auditing

**Repository:** `create-forge`  
**Priority:** P2  
**Planning baseline:** 21 September 2026

## Outcome

Add actionable dependency-vulnerability auditing with the acceptance evidence below.

## Issue context

This work comes from the 21 September 2026 engineering review. Live reconciliation on 21 September confirms forge-template 0.6.0 is published, create-forge PR #186 is merged and CF-21.01 is closed; CF-21.02 and CF-21.03 remain open. Review observations must be rechecked against the implementation candidate.

`create-forge` owns CLI UX, ProjectSpec construction, source isolation, destination filesystem/Git/hooks and error presentation. `forge-template` owns descriptors, manifests, composition, generated content, provenance and in-memory update planning. Data flow: create-forge → ProjectSpec → forge-template discovery/render/plan → create-forge filesystem/Git finalisation.

## Problem statement

Dependabot and action pinning are present, but the review did not observe a repository dependency-vulnerability gate.

## Proposed resolution

Choose pip-audit or an equivalent maintained scanner, document enforcement and exception rules, and wire a repeatable audit into PR, scheduled and release checks.

## Scope

Implement the stated resolution and acceptance criteria in this repository; update affected living contracts in the same PR.

## Acceptance criteria

- [ ] Inventory runtime and development dependency groups including the optional legacy extra and the resolved provider dependency.
- [ ] Scan the actual resolved environments/exports with recorded scanner and advisory data versions; document Python/platform marker coverage and avoid credential-bearing output.
- [ ] Fail actionable unsuppressed findings; distinguish advisory-service outages from clean results and define explicit release handling.
- [ ] Allow only reviewed, scoped, expiring advisory exceptions with rationale/owner; test clean, vulnerable, exception-expired and service-failure cases.
- [ ] Keep scanning repository-owned; client scans its installed graph (including forge-template) while provider owns fixes to provider constraints. No copied provider audit pipeline.
- [ ] Document remediation and lower-bound review; a lock-only upgrade is not automatically a change to published support floors.

## Exclusions

No automatic dependency upgrades, broad suppressions, generated-project scanning product or claim that a clean audit proves security.

## Dependencies and blocking requirements

- No unresolved hard predecessor. Ready to plan; prioritisation is separate from blocking.

May follow Streamlit release; a discovered actionable vulnerability is triaged independently.
