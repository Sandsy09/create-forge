**Repository:** `forge-template`  
**Priority:** P2  
**Planning baseline:** 21 September 2026

## Outcome

Validate batch generated projects, updates and distributions with the acceptance evidence below.

## Issue context

This work comes from the 21 September 2026 engineering review. Live reconciliation on 21 September confirms forge-template 0.6.0 is published, create-forge PR #186 is merged and CF-21.01 is closed; CF-21.02 and CF-21.03 remain open. Review observations must be rechecked against the implementation candidate.

`create-forge` owns CLI UX, ProjectSpec construction, source isolation, destination filesystem/Git/hooks and error presentation. `forge-template` owns descriptors, manifests, composition, generated content, provenance and in-memory update planning. Data flow: create-forge → ProjectSpec → forge-template discovery/render/plan → create-forge filesystem/Git finalisation.

## Problem statement

Rendering a sample project does not prove accepted compositions, distributions or update safety.

## Proposed resolution

Run the approved matrix using the capacity policy, built artefacts and an independent consumer.

## Scope

Implement the stated resolution and acceptance criteria in this repository; update affected living contracts in the same PR.

## Acceptance criteria

- [ ] Validate every accepted composition in the exhaustive tier and representative generated-project execution on supported Python/Linux/Windows.
- [ ] Run deterministic sample jobs without a scheduler/network service; assert outputs, exit codes and overwrite/failure safeguards.
- [ ] Build/install wheel and sdist; verify manifest/resources, clean facade imports and independent-client generation.
- [ ] Exercise provenance reproduction, planned updates, user data/local-edit preservation and required legacy regressions.
- [ ] Record exact commits, artefacts, matrix counts, durations and all failed/excluded cases before sign-off.
