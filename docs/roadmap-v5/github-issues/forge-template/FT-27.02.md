Data flow: create-forge → ProjectSpec → forge-template discovery/render/plan → create-forge filesystem/Git finalisation.

## Problem statement

The project shape must fit existing capabilities and update contracts without inheriting another archetype's private resources.

## Proposed resolution

Specify manifest rules, option schemas, capability/platform compatibility, generated commands and update/release evidence.

## Scope

Implement the stated resolution and acceptance criteria in this repository; update affected living contracts in the same PR.

## Acceptance criteria

- [ ] Enumerate accepted/rejected combinations with all current capabilities/platforms; reuse only published Foundation extension points.
- [ ] Define generated run/test/lint/type-check tasks, Scientific Python optionality, non-network smoke examples and deterministic fixtures.
- [ ] Specify owned paths, user data exclusions, provenance/skip-if-exists behaviour, supported update/rename rules and local-edit preservation.
- [ ] Set packaging, supported Python/Windows/Linux, independent-client and exhaustive validation requirements with projected matrix growth.
- [ ] Record any required protocol/version changes explicitly; no assumed compatibility or provider-specific production branches in create-forge.

## Exclusions

No provider implementation or client adoption before its respective gate.
