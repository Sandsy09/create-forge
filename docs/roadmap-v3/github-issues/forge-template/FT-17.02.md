# FT-17.02 — Implement approved platform compositions

## Outcome

Deliver catalogue-owned selection and compatibility rules.

## Issue context

The released baseline is create-forge 0.3.2 with default direct-Copier
generation and an optional, hidden engine preview over forge-template
>=0.4.1,<0.5. Preview generation does not provide engine-native updates. This
draft describes future work, not a shipped interface.

Provider manifests, composition, generated content and in-memory validation
stay in forge-template. Client UX, ProjectSpec construction, staging,
filesystem application, Git/hooks and error presentation stay in create-forge.

## Problem statement

Deliver catalogue-owned selection and compatibility rules. The current release
does not establish completion of this requirement; it needs the evidence and
ownership checks below.

## Proposed resolution

- Read the accepted predecessor contracts and implement only this issue's
  assigned outcome through the owning repository boundary.
- Add executable evidence for each acceptance criterion and update affected
  living documentation. Stop for a contract decision if required behaviour is
  still unresolved.

## Acceptance criteria

- [ ] Implement only Stage 15-approved platforms, requirements/conflicts and
  Foundation extension points.
- [ ] Prove valid compositions deterministic and invalid combinations
  rejected before render; clients consume descriptors without duplicating
  rules.
- [ ] Keep unrelated archetypes and capability-free output protected by
  regression fixtures.

## Review obligations

These review criteria apply to this issue's assigned slice; other listed
owners complete the remaining slices. Decision-issue exclusions apply to the
decision itself, not to the entire delivery roadmap.

### FT-ROADMAP-01-AC-03

Owners: [FT-15.03](https://github.com/Sandsy09/forge-template/issues/148), [FT-17.02](https://github.com/Sandsy09/forge-template/issues/151).

## Exclusions

- No CLI flags/prompts, client configuration, Git/hook execution or
  destination finalisation in the provider.
- No package publication in this issue; its separate release child owns
  publication.
- No arbitrary remote component registry or plugin execution; no new shared
  Forge runtime dependency for generated projects.
